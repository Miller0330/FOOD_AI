# Matrix 技術驗證：NPU 推論延遲（第 2 部分）

量測對象：100 類偵測模型（YOLO11s／512px，`.nb`，2 個 NPU 核心），由常駐程序 `matrixrt_yolod` 提供服務。
板子：Realtek Matrix RTD2811（2× Cortex-A73，CPU 調速器 schedutil）。測試時停掉 `riv-foodai`，板上沒有其他負載。
腳本：`benchmark/bench_yolod_board.py`、`bench_cpu_torch_board.py`；原始結果 `benchmark/bench_yolod_results.json`。

## 方法
- 資料：UEC FOOD 100 驗證集 2,109 張（真實的圖片大小與內容，而不是同一張圖重複測）。
- 每個設定先暖機 5 張，再完整跑 2,109 張，逐張記錄：
  - 板端程序內的分段計時：讀圖（imread）、前處理、NPU 推論、後處理（解碼＋NMS）。
  - 從 Python 送出請求到收到回覆的來回時間（含管線傳輸）。
- 長時間測試：以現行設定重複輪播驗證集 10 分鐘，每 30 秒記錄 CPU 溫度與延遲。

## 結果一：單張延遲拆解（現行設定：拉伸＋單類別解碼，n = 2,109）

| 階段 | 平均 | p50 | p95 | p99 | 最大 |
|---|---|---|---|---|---|
| 讀圖（JPEG 解碼） | 4.27 ms | 3.58 | 9.66 | 12.76 | 33.0 |
| 前處理（縮放＋轉換） | 2.76 ms | 2.72 | 3.57 | 3.92 | 4.5 |
| **NPU 推論** | **9.98 ms** | 9.98 | 10.19 | 10.25 | 10.5 |
| 後處理（解碼＋NMS） | 4.07 ms | 4.06 | 4.16 | 4.21 | 4.4 |
| 程序內合計 | 21.11 ms | 20.40 | 27.19 | 30.05 | 50.4 |
| **Python 來回總時間** | **21.35 ms** | 20.64 | 27.43 | 30.29 | 50.7 |

- 吞吐約 **46.7 張／秒**（單一請求序列處理）。
- NPU 推論非常穩定（σ 0.15 ms，p99 與平均只差 0.3 ms）；延遲的波動幾乎全來自讀圖（取決於 JPEG 大小）。
- **NPU 推論只占總時間約 47%**，其餘一半以上是在 CPU 上的讀圖、前處理與後處理。再往下優化的重點已經不是 NPU，而是 CPU 端。
- 與先前每次呼叫重新載入模型的舊做法（414 ms）相比，常駐化後為 21 ms，約快 19 倍。
- 冷啟動（啟動程序到可接受第一個請求）：約 0.29–0.47 s（5 次：467、296、293、295、293 ms）。

## 結果二：NPU 與 CPU 比較（同一個模型，浮點 TorchScript，板上 2 顆 A73）

| 執行方式 | 單張推論 | 相對 NPU |
|---|---|---|
| NPU（量化 `.nb`） | 9.98 ms | 1× |
| CPU，2 執行緒（torch 2.5.1，浮點） | 1,748 ms（σ 9.7） | 約 175× 慢 |
| CPU，1 執行緒 | 2,114 ms | 約 212× 慢 |

CPU 版是浮點、NPU 版是量化，兩者精度略有不同（見第 1 部分，量化損失約 0.002 mAP50）；CPU 跑法也不是最佳化過的，所以倍率只代表「在這塊板子上直接用 CPU 跑同一個模型」的量級。用 NPU 後，這個模型才有實用的即時性。

## 結果三：精度優化選項的延遲代價（各跑完整 2,109 張）

| 設定 | 來回平均 | p99 | 前處理 | 後處理 | mAP50 |
|---|---|---|---|---|---|
| 現行：拉伸＋單類別 | 21.35 ms | 30.3 | 2.76 | 4.07 | 0.682 |
| letterbox＋單類別 | 21.82 ms | 30.9 | 3.13 | 4.11 | 0.719 |
| 拉伸＋多標籤 | 21.39 ms | 30.4 | 2.76 | 4.07 | 0.703 |
| **letterbox＋多標籤** | **21.78 ms** | 30.6 | 3.13 | 4.08 | **0.741** |

letterbox＋多標籤只多 **約 0.4 ms**（前處理多 0.4 ms），換來 mAP50 **+0.059**，精度見 `VALIDATION_QUANTIZATION.md`。

## 結果四：長時間穩定性（現行設定，10 分鐘，28,032 張）

- CPU 溫度 **41–42 °C**，全程沒有升溫趨勢。
- 每 30 秒窗口的平均延遲介於 21.17–21.63 ms（第一個窗口 21.49，最後一個 21.63），沒有退化。
- 板上只有一個溫度感測器（`rtk-thermal`），沒有 NPU 專屬溫度或功耗讀數，所以無法回答功耗問題。

## 限制
1. 量測的是偵測器，不含 Flask、HTTP、網頁渲染；整個 `/detect100` 請求的時間（含 LLM 以外的網頁處理）先前量到約 0.06 s。
2. 只測了 2 核心的設定；這個 `.nb` 需要 2 個核心，無法比較 1 核心。
3. CPU 基準使用 torch 浮點模型，沒有嘗試量化 CPU 版或其他推論引擎（如 onnxruntime／NCNN），倍率會因最佳化程度改變。
4. 沒有 NPU 專屬溫度與功耗數據；10 分鐘的測試不能代表更長時間（例如數小時）的行為。
5. 與 LLM 同時運作時的偵測延遲沒有重測（先前只確認兩者可共存、請求仍能快速完成）。
6. 板子的 USB 網路在重開機後常常不會恢復，需拔插 USB 線；這影響維運，不影響上述延遲。
